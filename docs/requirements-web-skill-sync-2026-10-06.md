# Web 与 Skill 共用进度：需求文档

日期：2026-10-06  
状态：分析与方案草案，尚未实现  
配套文档：[优化指南](E:/Projects/repos/opensource-mentor/docs/optimization-web-skill-sync-2026-10-06.md)

## 1. 需求结论

保持 OpenSource Mentor 的 Web 入口，把现有能力提供给用户自己的 agent / harness，通过对话完成调用；同时把需要延续的贡献状态统一保存到 Supabase，使用户能够在网页、不同设备和 agent 之间继续同一个任务。

建议推进顺序：**明确状态归属 → 建立服务端任务与进度存储 → 接通 Web 恢复 → 提供 Skill 对话入口 → 验证跨端接续。** Skill 是使用入口，业务 API 提供能力，Supabase 保存业务事实。单独打包 `SKILL.md` 不会解决进度割裂。

本轮只交付需求与设计。下文的表结构、接口、安装方式和指标均为拟议方案，不能理解为现有功能或已经验证的线上表现。

## 2. 背景与范围

项目已有仓库分析、Issue 推荐与解释、贡献指南、AI 导师、PR 草稿和代码审查。当前重点是降低访问、授权、配置和恢复任务的成本，不继续扩展业务功能。

纳入范围：

- 保留 Web，支持现有能力从对话调用。
- 保存和恢复当前任务、指南内容与勾选进度、导师业务会话、PR 输入与草稿、审查结果。
- 统一用户身份、任务上下文、权限及跨端状态语义。
- 设计首次授权、后续复用、授权撤销、旧浏览器数据迁移和同步失败体验。
- 明确宿主兼容条件、发布方式、服务版本与 Skill 版本的关系。

不纳入本期：新增推荐算法、在线 IDE、自动提交或合并 PR、完整 agent 聊天历史托管、所有宿主一次性适配、所有 AI 能力离线运行，以及强制替换现有登录体系。

“安装到 agent”指安装调用入口与必要客户端资源；默认仍连接已有托管服务。自行部署完整后端作为开发者选项，不应成为普通用户的前置步骤。

## 3. 分析依据与边界

依据是当前仓库代码、README、现有 Supabase 迁移文件和官方技术文档。没有查询生产数据库、读取用户浏览器数据、实测线上登录或改动部署。

因此，本文区分：

- **代码确认**：当前仓库里可以直接证明的行为。
- **影响推断**：由存储生命周期、接口和状态结构推导的风险。
- **待验证**：生产迁移、配置、用户实际数据与运行表现。

仓库已有 2026-09-07 的产品体验评审，本次重新核对相关代码，只聚焦同步与 Skill 化。当前已存在“我的贡献”页面和任务上下文导航，不把这些当作待新增页面。

## 4. 当前问题

### 4.1 状态保存覆盖不完整

| 对象 | 代码确认的保存位置 | 对用户的影响 | 目标归属 |
| --- | --- | --- | --- |
| 用户、开发者画像、部分贡献偏好 | Worker 经服务端 REST 客户端写入 Supabase；浏览器另有缓存 | 已有云端基础，但不能代表贡献过程已经云端保存 | Supabase 为准，客户端缓存 |
| 其他本地画像字段与 UI 偏好 | `user` store 的 localStorage；并非全部字段都在当前 PATCH 契约中 | 不同端可能看到不同偏好 | 逐字段决定是否同步，禁止整包盲传 |
| 当前仓库与贡献 Issue | 固定 localStorage 键 | 同浏览器通常可恢复；换设备、换 origin 或 agent 无法读取 | 服务端任务及当前任务指针 |
| 仓库分析与 Issue 解释 | Zustand 内存 | 页面刷新可能丢失结果，需要重新请求 | 已用于任务的结果保存为产物；候选缓存单独管理 |
| 指南内容、章节与行动勾选 | sessionStorage，按仓库与 Issue 编号分键 | 同标签页刷新通常可恢复；关闭后重新访问、新设备或 agent 无可靠恢复保证 | Supabase，按任务和指南版本保存 |
| 导师消息与指南上下文 | Zustand 内存，`sessionId` 尚无服务端映射 | 刷新后对话和卡点消失 | 任务内业务会话与必要上下文 |
| PR 输入、生成结果、人工编辑 | Zustand 内存 | 未提交草稿刷新后可能丢失 | 任务内草稿和输入 |
| 审查结果 | 前端内存；Worker Cache API 配置约 1 小时 TTL；Express 的 Map | 浏览器刷新后失去结果定位；缓存失效或进程重启后无法长期恢复 | Supabase 保存结果及审查来源 |
| GitHub Token、模型 API Key | 当前代码只留在页面内存；非敏感配置在 localStorage | BYOK 用户刷新后需重新输入；与进度丢失是两个问题 | 客户端凭据设施，独立于业务同步 |

不能概括为“所有数据重新打开网页都会丢失”：localStorage、sessionStorage 和内存的生命周期不同。真正缺少的是一套账号下、跨入口可访问的贡献状态。

README 仍描述 BYOK 密钥保存在浏览器本地，而 `settings.ts` 当前明确过滤密钥并在刷新后清除。后续需要统一文档和提示，避免用户误判保存结果。

### 4.2 任务缺少统一身份

当前“开始贡献”主要更新前端 Issue 与仓库选择，没有服务端 `contribution_id`。指南键使用仓库与 Issue 编号，也没有用户和版本信息。聊天、PR、审查各自持有上下文，缺少可靠的共同关联键。

影响包括跨账户本地数据混用风险、切任务后旧结果误关联，以及 agent 无法通过稳定标识恢复任务。风险需要场景验证，不等于已证明线上发生数据泄露。

### 4.3 现有登录不能直接用于 agent

Worker 使用 GitHub OAuth、自建 `app_users` 和 HMAC 签名的 HttpOnly `osm_session` Cookie；代码设置有效期为 30 天。当前不是 Supabase Auth 会话。

所以降低门槛不只是延长登录：还需要恢复原任务、明确会话失效、让 agent 获得适合程序调用的应用凭据。普通用户首次接入仍需要一次明确授权；目标是后续正常使用不反复打开网页。

GitHub PAT、宿主账号和 OpenSource Mentor 应用身份是不同概念。安装 Skill 或宿主已经登录，均不能自动证明其有权访问本项目的用户进度。

### 4.4 两个后端存在能力差异

Worker 当前有 `/api/me`、画像更新和 GitHub OAuth 路由；Express 路由入口没有对应应用身份与 Supabase 持久化路由。README 的“两套核心能力”不能解释为身份与同步已经对等。

Skill 首发必须指定同步服务地址；后续若支持 Express，自建服务也需要遵守相同身份、状态和版本契约。

### 4.5 进度概念混用

`roadmap.ts` 的 `percentage` 当前由已生成的章节比例计算，`completedSteps` 由已完成章节计算，行动步骤还有独立勾选。指南生成完毕不意味着用户完成贡献。

同步前应分清生成状态、章节状态和行动步骤状态，避免网页与对话用同一个百分比表达不同事实。

## 5. 用户场景与目标流程

| 场景 | 用户表达或动作 | 预期行为 |
| --- | --- | --- |
| Web 回访 | 关闭页面后继续贡献 | 校验会话，恢复任务与已保存产物，不因恢复自动重跑 AI |
| Skill 首次使用 | “帮我理解这个 Issue” | 发现 Skill、检查环境；公开分析在允许的策略下直接开始；需要个人进度时引导一次应用授权 |
| Web → agent | “继续我昨天在网页做的任务” | 读取同账号任务；一个明确目标时直接恢复，有歧义时简短选择 |
| agent → Web | “已完成这一步，保存一下”后打开网页 | 对话根据明确指令更新步骤；网页下次刷新或恢复焦点时显示服务端已提交状态 |
| 指定任务 | “继续 owner/repo 的 #123” | 校验任务归属并恢复；不存在时明确提示并询问是否开始，避免恢复与新建混淆 |
| 双端编辑 | Web 编辑 PR，agent 同时更新指南 | 不同对象的更新可并存；同一字段冲突时保留双方内容并提示 |
| 授权到期 | “继续任务”但凭据过期 | 优先自动续期；无法续期时保留请求目标，完成授权后接续 |
| 网络失败 | 勾选步骤后保存失败 | 显示未同步，保留本地待提交操作；恢复网络后安全重试 |

典型流程：

```text
安装 Skill → 对话表达目标 → 检查能力与应用授权
                                  ↓
                      读取用户、任务、已保存上下文
                                  ↓
                         调用现有业务能力
                                  ↓
                      提交结果或明确的进度更新
                                  ↓
                   告知结果、保存状态和可继续的位置
                                  ↓
                        Web / agent 均可接续
```

## 6. 功能需求

P0 为跨端同步与正式 Skill 发布的必要条件；P1 为降低使用成本的后续优化。先验收 Web 存储，再验收对话入口，不要求一次性交付所有阶段。

| 编号 | 优先级 | 要求 | 可验收结果 |
| --- | --- | --- | --- |
| R01 | P0 | 统一账号与任务标识 | Web 与 agent 的凭据映射同一 `app_users.id`；客户端不能指定其他用户写入 |
| R02 | P0 | 建立服务端任务 | 开始贡献返回稳定任务 ID；重复请求不会重复创建同一活动上下文 |
| R03 | P0 | 保存指南与行动进度 | 内容、章节状态、步骤勾选分开保存，关闭页面后按版本完整恢复 |
| R04 | P0 | 保存已有工作产物 | 任务关联的解释、导师业务消息、PR 输入/编辑稿、审查结果可恢复；独立工具结果允许没有贡献 Issue |
| R05 | P0 | 显式保存状态 | 只有服务端提交成功才显示“已同步”；失败、待提交和冲突均有可操作反馈 |
| R06 | P0 | 跨端恢复与切换 | 恢复时读取最新服务端状态；切任务不混入上一任务的消息、草稿或迟到结果 |
| R07 | P0 | 防止覆盖与重复写入 | 支持版本校验和幂等；冲突不整包覆盖；请求重试不重复追加消息或生成任务 |
| R08 | P0 | 程序调用授权 | 首次授权、续期、撤销及按服务区分凭据；凭据不要求复制网页 Cookie |
| R09 | P0 | Skill 调用现有能力 | 分析、推荐/解释、指南、导师、草稿、审查的调用结果与 Web 使用同一业务契约 |
| R10 | P0 | 对话恢复明确且可核验 | “继续贡献”从服务端读取上下文；记录真实任务 ID、保存版本和更新结果，不依赖 agent 记忆推测 |
| R11 | P0 | 旧数据迁移 | 登录后预览可迁移的本地任务；归属不明的数据经用户选择导入；导入成功前不删除本地副本 |
| R12 | P0 | 用户与任务隔离 | 退出/换账号后清理相关内存与缓存；旧请求不能写入新账号或新任务；越权读取/写入拒绝 |
| R13 | P1 | 减少首次配置 | 托管模式只需安装和应用授权；BYOK 为可选；自托管配置与普通路径分开 |
| R14 | P1 | 宿主适配与诊断 | 公布实测宿主、运行时、网络/文件权限要求；错误给出具体下一步 |
| R15 | P1 | 非敏感偏好一致 | 云端保存业务相关偏好，设备相关显示选项可本地保留；密钥不随偏好同步 |
| R16 | P1 | 简化返回路径 | Web 登录回到原任务；已登录回访优先继续贡献；Skill 输出给出对应 Web 地址 |

首次范围以当前核心字段为准，不为云端同步强行保存所有 Zustand 状态。弹窗展开、动画、计时器、请求对象、临时流式片段等不属于业务事实。

导师同步保存本项目的业务消息与明确上下文，不默认上传用户在 harness 中与其他任务有关的整个聊天记录。独立工具首次范围至少保存输入、结果和恢复定位，完整历史管理界面暂缓。

## 7. 非功能与兼容要求

### 数据一致性

- 对用户明确显示“已同步”的操作，后续重新登录或换端必须能恢复。
- 本地响应可以乐观更新，但服务端确认前保持待同步标记。
- 长任务重试与指南重新生成保留已有可用结果；旧生成版本不得覆盖新版本。
- 云端不可用时允许查看已缓存内容；对未落盘、未提交内容不作永久保存承诺。

### 授权与数据访问

- 应用身份从有效凭据解析，不从请求体 `user_id` 推断。
- 新任务表、关联产物、导入、查询审查 ID 均执行归属校验。
- Supabase secret/service_role key 只用于受控服务端；不能打包进 Skill、客户端脚本或提供给用户。
- 用户密钥和应用凭据不进入业务表、普通日志、URL、模型上下文或仓库。
- 托管同步与凭据传递使用 HTTPS；当前 README 的 HTTP Docker 示例不能作为正式远程授权路径。

### 体验和性能

- 已保存的进度恢复不依赖重新生成画像或调用 LLM。
- 缺少画像时优先使用已有偏好与明确任务继续已有流程。
- 初版通过任务进入、页面恢复焦点和写入后重读实现更新；不把毫秒级实时协同作为必需条件。
- 建议测试环境目标：停止输入后 2 秒内发起草稿保存；健康网络下恢复任务 p95 不超过 3 秒。两者是待基线校准的目标，不是当前 SLA，LLM 生成和外部授权另行计时。

### 宿主兼容

采用通用 Agent Skills 目录结构，但格式兼容不代表执行环境、安装路径、凭据设施和工具权限一致。用户已确认首批验证 Codex 与 Claude Code；分别验证安装、脚本执行、网络访问、凭据管理和跨端接续，测试结果出来前不宣称已经兼容。

技能的格式依据见 [Agent Skills specification](https://agentskills.io/specification)。Skill 负责流程指导，服务端负责实时数据和受控动作的职责划分参考 [OpenAI 官方 Skills 文档](https://developers.openai.com/plugins/concepts/skills)。

## 8. 验收场景

| 编号 | 操作 | 通过标准 |
| --- | --- | --- |
| A01 | Web 选择 Issue、生成指南、完成两步；确认同步后关闭浏览器再开 | 恢复同任务、同指南版本和相同步骤；无需重生成 |
| A02 | 同账号换浏览器或设备 | 已同步任务、草稿和进度一致；设备上的密钥配置可独立 |
| A03 | agent 授权后说“继续贡献” | 恢复 Web 的任务、阶段和待办；结果含实际服务端标识 |
| A04 | agent 明确标记一步完成后回到 Web | 下一次刷新或焦点恢复拉取后呈现更新；不会把所有章节标成完成 |
| A05 | 两端编辑同一个草稿字段 | 检测版本冲突，保留两份内容供选择；不静默覆盖 |
| A06 | 两端分别更新不同步骤；其中一端撤销勾选 | 无冲突更新可安全合并；同一步冲突明确提示；撤销语义有效 |
| A07 | 写入成功但响应丢失，客户端重试 | 返回同一操作结果；不重复消息、任务或生成工作 |
| A08 | 断网修改，恢复连接 | 未同步内容仍可见，重试基于最新版本；无误报成功 |
| A09 | 账号 A 退出、账号 B 登录；A 的旧请求迟到 | 不显示或导入 A 的数据；旧结果被丢弃或留在 A 的隔离队列 |
| A10 | 导入旧 sessionStorage/localStorage，连续执行两次 | 用户可核对归属与内容；导入不重复；确认云端保存前本地副本保留 |
| A11 | 审查缓存过期或 Express 进程重启后恢复 | 已云端保存的结果可读取，标明基准版本和生成来源；缓存缺失不导致永久丢失 |
| A12 | 越权使用他人的任务、消息、草稿或审查 ID | 服务端拒绝；不能通过猜 ID 或修改嵌套字段访问 |
| A13 | 应用授权到期、撤销或服务地址更换 | 自动续期或要求重新授权；原目标保留；凭据不会误发给新服务 |
| A14 | 长生成中关闭页面、章节重试或切换任务 | 已完成章节可恢复；未完成部分显示实际状态；旧结果不覆盖新任务 |
| A15 | 不关联 Issue 使用现有独立工具 | 不被任务模型强制要求虚构 Issue；输入和产物可按独立记录恢复 |

## 9. 分阶段交付

| 阶段 | 交付范围 | 进入下一阶段的条件 |
| --- | --- | --- |
| S0：分析定稿 | 确认字段归属、首批宿主的环境要求、主服务地址、授权路线、迁移规则 | 需求与契约无关键歧义 |
| S1：Web 可靠保存 | 任务 ID、指南/行动进度、服务端版本、保存状态、旧数据迁移 | A01、A02、A05–A10、A12 相关部分通过 |
| S2：完整恢复已有产物 | 业务消息、PR 输入/编辑稿、解释、审查结果与生成检查点 | 任务切换和中断恢复通过；A11、A14、A15 通过 |
| S3：Skill 首发 | 程序授权、客户端适配、现有能力路由、对话恢复、宿主安装说明 | A03、A04、A07、A12、A13 通过；首批宿主实测 |
| S4：门槛优化 | 安装诊断、授权续接、必要的刷新优化、偏好同步 | 基线显示访问与恢复成本下降 |

进度可靠性是 Skill 首发的前置条件。可以提前设计 Skill 文案或用只读原型验证交互，但不把两个入口状态仍然独立的版本视为最终交付。

## 10. 成功指标与待决策项

先采集基线，再评估：首次完成有价值调用耗时、首次配置步骤数、重复授权比例、已同步内容恢复成功率、跨端接续成功率、保存失败率、冲突解决率，以及因无法恢复而重复生成的次数。

验收数据集中，“已同步”内容丢失和跨账号读写应为零；线上指标需要定义样本、观察窗口和失败分类，不能用一次体验代替总体表现。仅记录必要的脱敏 ID、状态、耗时和错误码，不记录聊天正文与密钥。

待实施前明确：

1. Codex 与 Claude Code 首批支持的操作系统与运行方式；是否允许安装额外运行时。
2. 首发主服务是否选择现有 Worker；Express 同步支持是否后置。
3. 客户端授权采用应用配对还是统一 OAuth/OIDC；是否接受将身份体系迁移作为独立项目。
4. 默认复用平台 AI/BYOK，还是另行提供宿主模型执行方式；后一项应单独评估，不能假定能读取宿主模型密钥。
5. 聊天、草稿和审查内容的保留/删除规则；不同部署是否确实连接同一 Supabase 与用户命名空间。
