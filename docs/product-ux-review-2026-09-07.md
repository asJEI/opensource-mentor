# OpenSource Mentor 产品体验优化报告

评估日期：2026-09-07。代码基线：`a3142a5`。范围：产品定位、用户旅程、功能、UI/UX、支撑体验的技术能力；不包含商业化方案。

## 1. 核心判断

项目已经具备一个开源贡献产品的主要组成部分：GitHub 登录与画像、Issue 推荐、仓库分析、分章节贡献指南、AI 导师、代码审查、PR 草稿。下一阶段最值得投入的是让用户能够持续完成一次真实贡献，并在隔天回来时继续推进。

建议把产品主线明确为：**帮助具备基础编程能力、缺少开源协作经验的开发者，找到值得做的任务，并完成从理解到提交、修改和复盘的全过程。** 完全没有编程基础的用户可以走文档或数据类贡献路径；熟练贡献者可以直接导入 Issue 或 PR，跳过教学步骤。

目前最明显的体验缺口是任务连续性、推荐解释质量、等待反馈和移动端信息密度。增加更多独立 AI 功能的优先级应低于这四项。

## 2. 评估依据与边界

- 浏览器实际检查：线上首页、会话恢复、登录后的推荐列表及详情、仓库分析空状态、PR 草稿空状态。
- 响应式检查：推荐页桌面视图和 390 × 844 手机视图，并读取页面布局尺寸。
- 代码检查：主要页面、导航与弹窗、状态管理、AI 请求、GitHub 候选筛选、OAuth 后台画像与持久化。
- 校验：`npm test` 的 4 个测试文件、20 项测试通过；Worker 独立 TypeScript 检查通过；完整 `npm run typecheck` 在前端报 3 处错误。
- 本次没有重新执行 OAuth 授权，没有发布 PR、提交外部评论或修改账户偏好；没有测量生产 API 延迟分布、查询生产数据库、完成真实贡献或开展用户访谈。
- 线上界面与本地实现进行了交叉核对，但没有核验线上部署 SHA。单次推荐样本不能代表所有用户或长期推荐质量。

下文“已观察”指本次线上现象，“代码确认”指静态实现证据，“建议”是尚待用户测试验证的设计判断。

## 3. 应当保留的优势

1. **选定 Issue 后已有上下文传递。** 仓库分析、指南、审查和 PR 草稿能接收当前任务，后续可在这个基础上建设贡献工作区。
2. **指南已经考虑渐进生成与失败恢复。** 有章节缓存、单章重试、步骤勾选和向导师带入卡点的能力，不需要重新从零设计。
3. **推荐不只依赖标签。** 已考虑技术、难度、时间、任务清晰度、仓库信号、分配和认领信息。优化应加强证据质量和用户控制，而非只改提示词。
4. **画像已经移出登录关键等待路径。** 代码保留 request_id 日志，后台有状态更新和规则兜底，这是正确基础。
5. **代码审查有真实数据和降级机制。** 共享审查逻辑、规则回退和现有测试值得保留。
6. **视觉语言已有统一基础。** 设计变量、紧凑侧栏、代码式信息表达适合开发工具；下一步应提高可读性和一致性。

## 5. 按用户旅程优化

### 5.1 首次访问与登录

首页已经说明了“找到 Issue，然后做完”的价值，但预览主要是模拟终端和示例文案。建议展示明确标注的真实产品示例：一个任务、它为什么适合、第一步是什么、最终产物是什么。示例匹配分数和时间必须标为示例，不能让人误以为已经分析了当前用户。

提供两个清晰入口：“帮我找任务”和“我已有仓库 / Issue”。前者接推荐，后者保留粘贴链接并在授权结束后返回原目标。已有活跃任务的回访用户优先进入“继续贡献”。

现有四步偏好问卷可保留跳过能力。建议先收集目标、技术与可用时间，其余按场景补充。画像未生成时使用用户已填写偏好和通用候选；画像完成后提示“推荐条件已更新”，不要在用户阅读过程中突然替换列表。

### 5.2 开发者画像

将“GitHub 观察到的事实”“系统推测的能力”“用户现在想做什么”分开呈现。公开仓库少不等于能力弱，公开记录与当前目标也不总是一致。

侧栏现在突出显示等级和百分比把握度，容易让推断显得过于精确。建议侧栏优先显示当前任务或目标；画像页显示证据来源、更新时间、可编辑偏好，以及“公开资料不足”等解释。

现有规则兜底可以返回 ready，应同时区分生成来源，例如规则初判与 AI 补充。ready 表示结果可用，不应暗示 AI 已完成分析。重新生成应保留上一份可用画像，并提供独立重试，避免要求用户重新授权。

### 5.3 Issue 发现与决策

推荐页的首要工作是帮助用户比较任务。建议列表保留：任务标题、仓库、实际改动类型、技术要求、时间范围、可参与状态、一条最有区分度的匹配原因。展开后再展示原文、依据和风险。

“可以开始”的现有解释是未发现分配或认领信号，这个边界应直接可见。缺少信号不能证明无人参与；开始前应刷新 Issue 状态并提示查看近期讨论。不要把点击“开始贡献”称为 GitHub 认领成功。

增加以下控制：技术栈、时间、文档 / 测试 / 功能类型、难度、收藏、暂不感兴趣。反馈提供简短原因，例如太难、太简单、不想用该技术、已经有人在做，用于下一批排序。

目前仓库健康度部分依赖 stars、forks 和更新时间。后续应优先验证维护者近期响应、类似 PR 的处理情况、贡献文档和测试说明；数据不足时明确未知。不要把热门项目等同于新手友好。

为每条推荐生成与用户选择相关的原因，例如：“你选择了 TypeScript 和 1–3 小时；此任务主要修改一处类型定义，已有相关测试，但需确认兼容性。”仅在数据支持时给出具体结论。

列表当前会随单项分析结果更新排序。建议用户展开任务或开始滚动后保持顺序，待批次结束提供“按最新匹配排序”，避免阅读目标移动。

### 5.4 贡献工作区

建议新增“我的贡献”作为回访入口，以一个任务为中心组织现有页面。任务顶栏始终显示仓库、Issue、分支 / PR（若已关联）、当前阶段、保存状态和下一步。

建议阶段：理解任务 → 准备环境 → 实现与验证 → 提交 PR → 回应审查 → 复盘。允许跳过、返回和标记受阻，不要求熟练用户逐项完成教学。

每一步采用统一结构：本步目标、操作、预期结果、验证方法、卡住时求助。例如“运行测试并确认相关用例通过”，比单纯勾选“已阅读测试说明”更能代表实际进展。

代码阅读和修改继续发生在用户熟悉的本地工具中。产品负责保存上下文、解释和验证清单，先做好链接与命令交接。在线 IDE 和自动代写可以暂缓。

### 5.5 AI 导师

保留独立聊天页，同时在指南和审查详情中提供就地提问入口。自动携带当前 Issue、步骤、相关代码位置和用户选择的错误信息，并让用户看见本次引用的上下文。

优先接通真正的流式输出。当前 isStreaming 只是等待状态，消息仍在完整请求结束后一次加入。底层已有流式接口和指南流式路径，可复用现有模式。

补充 Markdown、代码块、复制、长代码横向滚动和来源链接。回复应区分已读源码事实、根据描述推测、需要用户验证的建议。涉及未读取的文件时不要表现为已经确认。

支持“只给提示”和“分步指导”两种深度，把当前已有 guidancePreference 转化为用户可感知的交互差异。失败后允许重试上一条；停止后保留已有内容；聊天按贡献任务保存。

### 5.6 审查、PR 与后续反馈

代码审查已有真实 PR 和分支比较基础，后续应突出审查范围、基准提交、遗漏文件、规则降级和未执行测试，避免把“没有发现问题”解读为“可以安全合并”。

PR 草稿应结合用户确认的实际 diff、仓库 PR 模板、测试执行结果和关联 Issue。区分“建议运行的测试”和“确实运行通过的测试”，不自动声称完成未验证动作。

优先完善“复制标题 / 描述并跳转 GitHub”的交接，再关联用户实际创建的 PR。提交后承接维护者反馈、补充修改和合并状态；没有数据时允许用户手动标注，避免虚构进度。

复盘关注学到了什么、遇到什么阻碍、下一次适合做什么，而不只统计生成次数或展示徽章。

## 6. UI/UX 设计方向

### 信息架构

建议顶层导航收敛为：发现任务、我的贡献、独立工具、设置。进入贡献任务后，再提供概览、指南、导师、审查、PR 等上下文视图。现有独立工具保留直接入口，方便已有明确目标的用户。

主工作区以“下一步行动”为首屏核心。长篇项目概览、解释和历史信息放在次级区域。每个主要区域只突出一个主操作，其余使用次级按钮或菜单。

### 视觉层级

保留开发工具式的紧凑布局，减少反复出现的英文 eyebrow、固定“新”徽标和解释整页功能的长段落。将描述改为帮助用户决策的具体信息。

暗色界面应提高正文与次要文字的层级差异，长文阅读可考虑浅色模式。颜色承担一致语义：主操作、进行中、成功、风险、失败。是否改变品牌金色应以整体可读性测试决定，无需为了改版先换整套主题。

主文和指南可先试验 15–16px 中文字号，元信息 12–13px；这属于设计候选值，需在实际密度下验证。统一按钮高度、图标尺寸、边框与焦点样式。

### 移动端

先修复明确布局错误。推荐页 `.page-title-row > :first-child` 的 `flex: 1 1 380px` 在移动端改为纵向后把基础尺寸作用到高度，形成明显空白。应在窄屏重置尺寸规则。

当前移动端使用横向滚动导航，账号区域隐藏，后面的设置入口发现成本较高。建议采用“发现 / 当前任务 / 更多”的紧凑导航，更多中提供账号与工具。

手机优先支持筛选、收藏、阅读指南、查看进度和轻量提问。复杂 diff 提供单列视图；无需强行复刻桌面多栏工作区。大屏优先展示完整阅读和审查能力。

### 状态与无障碍

统一空状态、加载、部分成功、失败和过期状态。每种状态回答：发生了什么、已有内容是否保留、现在可以做什么。开发配置错误不应让普通用户去检查 Supabase 或 SESSION_SECRET，应显示简明错误和可供支持定位的 request_id。

导航使用链接，选项使用按钮或原生控件；弹窗添加 dialog 语义、标题关联、焦点限制和关闭后恢复；表单 label 与输入关联。键盘导航必须能够完成核心流程。焦点行为可依据 [W3C Modal Dialog Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) 验收。

## 7. 支撑产品体验的技术方向

### 可靠后台画像

OAuth callback 已不 await 画像，但后台任务仍依附当前 Worker 调用。HTTP Worker 的 waitUntil 在响应发送或客户端断开后最多延长执行 30 秒；慢 GitHub 请求和 LLM 重试可能超过该窗口。这是实现风险，本次没有复现超时取消。[Cloudflare 官方说明](https://developers.cloudflare.com/workers/runtime-apis/context/#waituntil)

近期应增加 generating 过期恢复、独立重试接口、幂等任务键与版本校验，避免旧任务覆盖新画像。需要可靠重试时采用队列或持久任务流程；当前最小权限和敏感信息不入日志的原则继续保留。

当前写入已尝试把结构化画像展平成数据库字段，同时兼容缺列并退回 JSON 保存。若数据库仍见空列，应核对线上迁移、实际列名、兼容回退日志及 JSON 内容，不能仅依据 OAuth 成功判断画像写入完整。本次未查询数据库，不能确认生产空值根因。

### 任务与状态模型

建立 contribution_id，关联用户、仓库、Issue、阶段、指南版本、聊天、审查结果和 PR 草稿。采用任务级自动保存与更新时间，用户输入优先于后台推断结果。访客可先本地保存，登录后提供明确迁移；不同账户的数据应隔离。

按仓库、Issue、提交版本缓存可复用分析；对进行中的任务保留历史版本。请求去重、取消过时请求、后台轮询退避和页面可见性控制，能减少等待和重复请求。缓存键必须包含影响结果的上下文，避免串任务或串用户。

### 性能观测

保留 request_id，补充贡献任务和后台任务的关联标识。区分服务端 callback 时间、浏览器完成跳转、首屏可操作、首个 token 和首段有用内容；redirect 日志只表示服务端构造响应，不能代表用户已经进入产品。

近期先测基线，再定服务目标。分别按冷 / 热缓存、画像新建 / 已存在、平台模型 / BYOK、移动 / 桌面统计 p50、p95、失败率和取消率。不要沿用此前单次登录 23.617 秒作为重构后表现，也不要将单次观测当作 p95。

## 8. 后续推进顺序

| 阶段 | 主要交付 | 完成判据 |
| --- | --- | --- |
| 第一阶段：修正确定性问题 | 会话恢复状态、移动端空白、PR 输入契约、复制反馈、类型检查 | 相关场景能稳定复现修复效果；核心页面无明显断路；本地构建校验通过 |
| 第二阶段：完成一次贡献 | 任务工作区、跨会话保存、导师流式输出、画像独立恢复、PR 交接 | 用户可开始任务，关闭页面后回来继续，完成验证并关联实际 PR |
| 第三阶段：提高推荐价值 | 多样性、明确筛选、证据化匹配理由、收藏与负反馈、任务状态复核 | 用户能说明为何选择任务；不合适推荐有反馈出口；处理失效和重复任务 |
| 第四阶段：形成持续使用 | 审查反馈处理、贡献历史、复盘、下一次任务、辅助能力完善 | 回访用户能继续处理已有贡献，或基于历史开始下一次贡献 |

推荐下一版优先画三类页面：发现任务、当前贡献工作区、提交与反馈。先用真实 Issue 内容验证信息架构，再统一视觉细节。

暂缓投入：完整在线 IDE、自动提交机器人、复杂徽章排行榜、大量独立 AI 工具、长期社交社区。这些可作为未来选项，但当前核心路径还有更直接的改进空间。

## 9. 如何验证改版是否有效

建议先招募 5–8 位具备基础编程能力的用户，其中包含首次开源贡献者与有少量 PR 经验者。这个样本用于发现操作问题，不用于证明统计显著性。

测试任务：选择一个适合 1–3 小时的 Issue；解释为什么选它；找到第一个可验证动作；遇到障碍时求助；关闭后恢复；整理一份不含虚构测试结果的 PR 描述。

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 首次有价值行动时间 | 进入产品到完成第一个有证据的行动，如复现问题或跑通测试 | 衡量是否真正帮助开始贡献 |
| 推荐接受率 | 开始贡献的独立用户 / 看到推荐的独立用户 | 检查候选是否有吸引力，需结合后续结果 |
| 任务恢复成功率 | 回访后成功恢复上下文的任务 / 尝试恢复的任务 | 验证保存能力 |
| 贡献推进率 | 从开始任务推进到验证、提交等阶段的比例 | 定位用户在哪一步停下 |
| 推荐不合适原因 | 太难、太简单、技术不符、任务失效等 | 解释排序和供给问题 |
| 有效贡献结果 | 已验证 PR、维护者要求修改、合并、关闭及用户主动终止 | 评价成果；合并受维护者因素影响，不单独作为成功标准 |

只采集完成上述验证所需的事件与脱敏标识，避免记录聊天正文、代码、token 或 cookie。先建立基线，再决定每阶段的改善目标。

## 11. 当前设计补充评审

本节根据本次已检查的线上界面与代码补充，供下一版设计直接使用；不是对尚未提供的新设计稿的验收。下面的验收标准是改版目标，尚未实现。

### 11.1 七项设计问题与修改要求

| 优先级 | 设计问题 | 修改要求 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 首屏没有尽快呈现任务。标题、说明、技术栈和搜索提示占据较多空间，手机标题区域约 436px | 修复移动端标题尺寸，压缩重复说明，将筛选和候选内容前移；搜索提示按需展开 | 在 390 × 844、默认字号、列表加载完成时，首屏能看到首条 Issue 的标题和主要判断信息；文字放大后可自然换行和滚动 |
| P1 | 导航按功能划分，用户需要自行判断操作顺序 | 在贡献工作区固定显示当前仓库、Issue、阶段和下一步；允许熟练用户直接进入审查或 PR 工具 | 用户从任一任务视图都能辨认当前任务、所在阶段，并直接继续下一步；切换视图不丢失上下文 |

### 11.2 下一版优先设计的三个页面

**发现任务：让用户选得明白。** 首屏优先展示任务和简洁筛选，每条候选包含具体改动、适合原因和参与状态。详情承接证据、原文、风险和“开始贡献”。同时设计画像生成中、没有合适候选、部分分析失败和任务失效状态。

**当前贡献工作区：让用户做得下去、回来能继续。** 顶部固定任务身份与保存状态，主体展示当前步骤和验证方法，就地提供导师帮助。包含暂停、受阻、跳步、恢复和切换任务状态；任务切换前明确未保存内容的处理方式。

**提交与反馈：让贡献形成完整结果。** 汇总实际改动、已执行验证、待确认事项和 PR 草稿，承接 GitHub 提交与 PR 关联。继续展示维护者反馈、补充修改和合并或关闭状态，未获取的信息明确留空或标为待确认。

### 11.3 设计交付要求

1. 三个页面先使用真实任务内容验证布局，再统一字体、颜色和组件细节；示例数据需明确标注。
2. 每个页面至少提供桌面和手机方案，并覆盖加载、空状态、失败、部分成功及恢复状态。
3. 提交原型时附一条完整路径：选择任务 → 完成一个可验证步骤 → 离开后恢复 → 整理 PR → 查看反馈。
4. 统一描述“本地选择任务”“GitHub 认领”“生成 PR 草稿”“实际创建 PR”，避免把不同动作表现成同一结果。
5. 首轮验收优先看任务是否易选、操作是否连贯、结果是否可恢复，再评估视觉精修效果。
